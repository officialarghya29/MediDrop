# Accessibility register

Last updated: 2026-11-20

Status: **PARTIAL. Public pages have an automated axe gate; Lighthouse, keyboard, screen-reader and role-dashboard audits remain open.**

This register records what exists in the code, what is missing and what must be proven before
the v5 WCAG AA claim. Static presence of an ARIA attribute is not a pass.

## 1. v5 requirements

- WCAG AA.
- Keyboard navigation.
- Touch targets at least 44px.
- Loading, empty, error and success states on every screen.
- axe zero serious/critical findings.
- Screenshots at 390px and 1440px.
- Light and Ops Night modes for pharmacy, delivery and admin.
- English, Hindi and Bengali UI.
- Honor `prefers-reduced-motion`.

## 4. 0.1.7 evidence

- Command: `cd frontend && npm run build && npm run test:e2e`.
- Tools: Playwright **1.65.1**, axe-core/playwright **4.14.0**, system Chrome **158**, 390 × 844 viewport.
- Scope: home, `/search?q=Paracetamol`, `/medicines/1`, `/login`, plus search → medicine detail.
- Result: **5 passed, 0 failed**; zero WCAG A/AA axe violations.
- The first run found a real `label-content-name-mismatch` on the logo. The implementation now relies
  on the visible wordmark and tagline instead of a partial `aria-label`; no rule was disabled.
- Limitation: deterministic public API fixtures. Pharmacy, delivery, admin, checkout, keyboard,
  screen-reader, 1440 px, Ops Night, i18n and Lighthouse remain outside this gate.

## 5. Required gate for M14

1. Extend the axe browser gate to checkout, tracking and every role dashboard.
2. Run Lighthouse on the customer home, search, checkout, tracking and admin screens.
3. Record a keyboard-only pass and a screen-reader pass.
4. Measure touch targets; fix failures rather than suppressing rules.
5. Add a skip link and complete modal focus trap/restore behaviour.
6. Add 390px and 1440px screenshots in light and Ops Night modes.
7. Add i18n and a PWA manifest/service worker, then re-run the gate.
8. Publish the exact tool versions and reports beside the result.
